## The floor held, and last night's prediction was wrong about the batch

Last night this file recorded that the Atlas ratchet's runway was one event and that "held at
79%, or at 85%, the gate refuses on the next ordinary night". The gate passed. The prediction's
condition is what failed, and the correction is worth having, because the quantity that decides
this is the arriving batch's dated share and not the corpus's.

Counted from the staged trunk rather than read off the summary line:

```
n=2474  explicit=2243  fell_back=231  pct=90.6629  → rounds to 90.7
```

Against 2026-09-04's `n=2456 explicit=2227 pct=90.6759`: 18 events arrived and 16 of them
carried an explicit date — **88.89%**, against last night's batch at 79%. The corpus fell
0.0130 pp, and the rounded figure is unchanged. Headroom to the `< 90.65` refusal boundary is
now **0.0129 pp**.

The runway is still one event, in the sense last night meant it: **a single undated event
arriving alone takes the rounded figure to 90.6 and the gate refuses.** What last night got
wrong is that arrivals do not come alone, and a batch's dated events buy room for its undated
ones. A batch of 18 arriving tomorrow needs 16 of them dated — 88.88% — to hold the line. That
is tonight's rate to two decimal places.

Repeating tonight's exact batch, 18 arrivals with 16 dated:

```
+1 night  90.6501%  → 90.7  PASS   (by 0.0001 pp)
+2 night  90.6375%  → 90.6  REFUSE
```

So the refusal is due on the second night from now if the feed keeps dating its arrivals exactly
as well as it did tonight, and on the next night if it does any worse. Tonight bought one night,
by a ten-thousandth of a point.

Nothing here is this project's to fix. The corpus, the baseline and the ratchet are the Atlas's,
and its own nightly task owns the refusal when it comes. On a refusal this build stops and the
sheet keeps serving `20260905-1131`, which is the designed behaviour.

## The drift printer was silent again, for the same reason

Second consecutive night. `audit_all.py` compares against `baselines.json:last_run`, the Atlas's
own nightly ran ahead of this one, and `last_run` now reads `date 2026-09-05, n 2474,
explicit_pct 90.7` — the identical corpus this run then read. Every tracked path hit
`now == was` and was skipped, so the step that mattered was never printed in the run this
project saw.

This is the same defect recorded on 2026-09-04, not a new one: **a baseline named for the last
run and used as though it meant yesterday.** It is worth noting that it is not a one-night
coincidence. A second reader of an unchanged corpus is structurally blind to that corpus's
drift, every night, for as long as two runs share a date. The fix belongs in the Atlas — key the
comparison to a date rather than to a run — and is noted here for whoever holds that decision.
