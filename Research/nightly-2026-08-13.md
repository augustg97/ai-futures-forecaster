## Supply stays at its priors

S is now the only axis whose marginals sit bit-exactly on round numbers — `0.35 / 0.33 / 0.32`
— and it carries four non-degenerate conditions:

```
S given C2: {S1 ×1.8}    S given E3: {S3 ×1.6}
S given C3: {S2 ×1.7}    S given E4: {S3 ×1.4}
```

An axis reweighted by those tables cannot land on its prior to fifteen significant digits.
Two of the four parents (C2, C3) sit *earlier* in the axis order than S, so this is a separate
thing from the later-parent drop the repair addressed: that one is fixed, and S is still flat.

The parent's own ensemble disagrees with its marginal table here. Over the 2000 sampled
world-lines S reads `0.3405 / 0.3215 / 0.3380` — S3 about 1.8 points above the table, in the
direction the E3 and E4 boosts predict. So the conditioning exists in the sampler and is absent
from the analytic table.

This matters to the sheet because the two files are drawn in different places: the controls draw
`marginals.today` (S at 35/33/32) while Alternatives draws sampled world-lines (S3 at 33.8%).
A reader comparing the two is reading two different distributions for the supply variable.

**Held, not applied** — S's priors live in the Atlas, and a fix belongs to `worldlines.py`.

Alternatives tab needs a line saying which of the two it is drawing.

## Note on `recommend()`

`recommend()` in `app.js` compares two constant tables, `PRIOR_R2` against `RESEARCHED`, so the
moves the Research tab reports are the true r2 → r3 moves and were unaffected by tonight's
drift. The comment above it describes reading the live prior, which the code does not do. It
reads correctly today because the applied network agrees with the researched figures; it would
go stale silently if the Atlas moved a prior again. Worth reconciling the comment with the code,
or the code with the comment, next time that file is open.
