## The two numbers in the refusal line are the same rule stated twice

The message names `baseline ≥ 91.7`; `HANDOFF.md` and the Atlas's own note call the floor 90.7.
Both are right and neither is the whole rule. `audit_all.py` compares
`r["events"]["explicit_pct"] < b["events"]["explicit_pct"] - 1.0` — the stored baseline is 91.7
and the tolerance is a flat 1.0, so the operative floor is **90.7**, tested against the value
already rounded to one decimal place by `check_events`. The printed message reports the stored
baseline without the tolerance it was compared under. A reader who trusts the line alone goes
looking for a 1.1-point fall that did not happen; the fall was 0.0429 pp, and it only refused
because it crossed a rounding boundary. Not this project's file to fix, but recorded here so the
next run does not re-derive it.

The sheet is now **0.0300 pp below the boundary**. It takes **8 consecutive fully-dated events**

ordinary batch of ten at 80%, the corpus keeps falling.

being enforced tonight against 2,484 events — a corpus 36% larger, whose composition the number
was never measured on. The ratchet's one-decimal comparison also means the stored 91.7 has not
